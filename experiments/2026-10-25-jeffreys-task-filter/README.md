# 先探测、再筛题：用 Jeffreys 后验给 RL 训练任务估难度

## 目的

Microsoft 与 Hugging Face 的博客 [Turning Database Grading into RL Rewards: Post-Training Agents with ThinkingBox](https://huggingface.co/blog/microsoft/thinkingbox-training) 在用 GRPO 训练 Agent 前，先让基座策略对每个候选任务反复试做，用 Jeffreys 后验 Beta(k + ½, n − k + ½) 估计成功率，按 0.08 / 0.40 / 0.60 / 0.90 分桶，丢掉几乎做不出（< 0.08）和几乎总能做对（≥ 0.90）的任务，训练池在整个训练过程中固定。

原因是：GRPO 一组 rollout 的奖励如果全是 0 或全是 1，组内没有差异，就没有学习信号。本实验用模拟数据演示「先探测、再筛题」能减少多少这样的零方差组。

注意：任务的「真实成功率」由脚本按固定随机种子构造，只演示机制，**不复现文章中的任何数字**。

## 步骤

1. 构造 600 个候选任务，真实成功率来自偏向两端的分布（很多题太难或太简单）
2. 每个任务探测 8 次，记成功次数 k
3. 用 Jeffreys 后验均值 (k + 0.5) / (n + 1) 估计难度（取均值是本实验的选择，原文没有说明用后验的哪个统计量），按上述边界分桶，去掉两端
4. 分别从「全部任务」和「筛选后任务」中抽 4000 组、每组 8 条 rollout，统计奖励全 0 或全 1 的组所占比例
5. 检查被丢掉的任务中，有多少真实成功率确实落在两端

运行：

```bash
python main.py
```

程序打印 `METRIC:` 指标、`[PASS]/[FAIL]` 检查和最后一行 `RESULT:`，任一检查失败时以非零状态退出。

## 预期结果

- 筛选后零方差组的比例明显低于筛选前
- Jeffreys 后验均值永远不会是 0 或 1（而直接用 k/n 会有大量 0 和 1）
- 被丢掉的任务多数确实过难或过易，但不是全部——只探测 8 次会有误判

## 启示与可以继续尝试

- 探测 8 次时，k = 0 的后验均值是 0.5/9 ≈ 0.056（< 0.08），k = 8 是 8.5/9 ≈ 0.944（≥ 0.90），所以这组边界在 n = 8 时等价于「去掉全错和全对的任务」；把 `N_PROBE` 改成 20 再看分桶如何变化
- 把 `GROUP` 调大，零方差组会变少，但每步的 rollout 成本更高
- 原文还观察到 RL 后 pass@1 上升、pass@20 略降，即模型「更稳定但不更广」——筛掉太难的题可能是原因之一，可以在模拟里给「太难」的题单独记账思考这一点
- 文章用 DAPO 风格把零方差组替换掉；筛题是在训练前做，两者可以叠加

## 内网复现

- **无需任何第三方依赖**，只用 Python 3.8+ 标准库，无需联网，可直接在内网运行
- 把 `main.py` 拷贝到内网机器执行 `python main.py` 即可
- 如要在真实任务上复现，需要能反复运行基座模型的推理环境和任务的自动评分器；ThinkingBox 的代码在 GitHub（github.com/microsoft/thinkingbox-training），需外网或内网 Git 镜像获取，本实验不依赖这些
