# 玩具实验：用两段式验收门筛出不能用的量化模型文件

## 目的

[quantcheck](https://github.com/aditi-p31/quantcheck) 是论文 *Broken on Arrival* 的配套工具：作者在 Ollama 官方库和 Hugging Face 社区文件里实际跑了 327 个代码模型文件，发现有的低比特量化版本一道题都做不对，而模型名和文件看起来都正常。它的 README 描述了一个两段式筛查规则：

- **第一段**：15 道 HumanEval+ 题的冒烟测试，通过数低于 9 的标为可疑
- **第二段**：和同一模型变体的高精度版本（q6_K / q8_0 / fp16）的中位数（组基线）比较；自身 ≤ 2 且组基线 ≥ 8 才判为不能用；组基线本身就低的，不下结论

本实验**不是 quantcheck 的代码，也不下载或运行任何模型**，只用 Python 标准库在 15 个手写的模拟文件分数上实现这套判定，另外实现了 README 里定义的重复度指标 `rep6`（最常见 6 词片段的次数 × 6 ÷ 总词数），看它能否区分「原地打转」的输出。

## 步骤

```bash
python main.py
```

程序先打印每个模拟文件的判定（pass / degraded / non-functional / unjudged），然后输出 5 项 `[PASS]/[FAIL]` 检查、`METRIC:` 指标和最后一行 `RESULT:`；任一检查失败时以非零状态退出。

## 预期结果

- 变体 A 的两个低比特文件（模拟「完全失效」）被判为不能用
- 变体 B 的低比特文件分数下降但仍可用，单阈值会标记它们，两段式门不会误判
- 变体 C 是本身就很弱的小模型，连 fp16 都只有几题，组基线不足 8，判为「不下结论」
- `rep6` 对重复同一句话的输出明显高于正常代码

## 局限

- 分数全部是手写的模拟值，只说明判定逻辑如何工作，不代表任何真实模型或量化文件的表现
- 冒烟测试只说明文件「能不能用」，不说明原因；quantcheck 作者强调归因需要重新量化后逐张量比对
- 阈值（9、2、8）照搬 README，换成别的题集或语言需要重新校准

## 启示与可以继续尝试

- 团队给内网模型仓库上新量化文件之前，可以加一道类似的验收：先跑十几道自己的业务题，再和同一模型的高精度版本比
- 组基线的思路也适用于对比不同推理后端（如 Ollama 与 vLLM）上同一模型的表现
- quantcheck 发现部分社区文件失分是因为缺少聊天模板，而非权重问题；验收时值得把模板也当作被测对象

## 内网复现

- 只用 Python 标准库，不需要安装任何依赖，`requirements.txt` 仅作说明
- 程序完全离线运行，不访问网络，也不需要 API key 或 GPU
- 如果要用 quantcheck 测真实文件：需要本地 Ollama 服务和 `evalplus==0.3.1`（可通过内网 PyPI 镜像安装）；`harness/audit.py` 会执行 `ollama pull`，内网需改为指向内网模型仓库，或先在外网机器拉取后导入
