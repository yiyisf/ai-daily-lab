# 给 MoE 批推理排个序：按领域分组能少读多少专家

## 目的

Hugging Face 社区文章 [Sort your prompts: a free speed-up for MoE batch inference](https://huggingface.co/blog/badaoui/sort-your-prompts) 指出：混合专家（MoE）模型的每个解码步，要读取批内**所有请求**路由到的专家权重。同一领域的提示词倾向于使用重叠的专家，所以离线批处理前先按领域（或嵌入聚类）给提示词排序，就能让每步读取的专家更少、解码更快——不改模型、不改内核。

本实验用模拟路由演示这个机制。注意：路由分布是脚本按固定随机种子构造的，只演示机制，**不复现文章中的任何数字**。

## 步骤

1. 设定 128 个专家、每个 token 选 8 个；6 个领域，每个领域有一组「偏好专家」被更频繁地选中
2. 生成 768 条提示词（6 个领域各占 1/6），批大小 32
3. 分别按「随机打乱」和「按领域排序」切批，每批模拟 20 个解码步，统计每步触达的不同专家数
4. 换成 32 个专家、每 token 选 4 个的粗粒度配置，重复比较
5. 统计单个领域内最常用的 1/4 专家占全部路由决策的比例

运行：

```bash
python main.py
```

程序打印 `METRIC:` 指标、`[PASS]/[FAIL]` 检查和最后一行 `RESULT:`，任一检查失败时以非零状态退出。

## 预期结果

- 按领域排序后，每步触达的不同专家数明显少于随机打乱
- 32 专家配置的节省比例小于 128 专家配置（与文章「粗粒度 MoE 收益较小」的观察方向一致）
- 单领域内前 1/4 专家占的路由比例高于均匀路由下的 25%

## 启示与可以继续尝试

- 「少读的专家数」只是上限估计：文章实测的提速约为按读取字节估算的一半，因为每步只有 MoE 部分变便宜
- 可以把领域偏好调弱（把权重 12.0 改小），观察节省如何缩小——这对应真实数据里领域边界不清晰的情况
- 可以把批大小调大，观察当一批几乎触达全部专家时，排序的收益如何消失
- 在线服务中排序需要攒一批请求，会增加排队延迟，文章也指出这类场景不适用

## 内网复现

- **无需任何第三方依赖**，只用 Python 3.8+ 标准库，无需联网，可直接在内网运行
- 把 `main.py` 拷贝到内网机器执行 `python main.py` 即可
- 如要在真实模型上验证，需要 vLLM、MoE 模型权重（如 Qwen3-30B-A3B）和 GPU；权重可通过内网的 Hugging Face 镜像下载，本实验不依赖这些
