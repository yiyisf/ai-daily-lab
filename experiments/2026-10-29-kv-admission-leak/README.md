# 玩具模型复现：被拒绝的超长请求进入 decode 导致跨请求泄露

## 目的

Cloudflare 在 [GLM-5.3 KV 缓存泄露复盘](https://blog.cloudflare.com/kv-cache-exposure-remediation/) 中写到两个叠加的原因：

1. 模型对外声明的上下文长度大于 prefill 节点 KV 池的容量；
2. SGLang 在 prefill/decode 分离模式下，把放不下的请求标记为 rejected 并换成 1 个 token 的占位，但入口队列只检查请求是否 finished，于是请求被放行到 decode，decode 读到了池子里其他请求残留的数据，客户端还收到 HTTP 200。

本实验用纯 Python 写一个**玩具模型**（不是 SGLang 代码）复现这个机制，并对比：

- 引擎修复：入口按 rejected 拦截，不做 KV 传输；
- 配置修复：KV 池容量不小于上下文长度（复盘里扩到约两倍）；
- 检测：只看状态码的测试 vs 在每个请求里放 canary 标记的测试。

## 步骤

```bash
python main.py
```

程序会打印每种配置下的泄露响应数（`METRIC:`）、7 项 `[PASS]/[FAIL]` 检查和最后一行 `RESULT:`；任何检查失败时以非零状态退出。

## 预期结果

- 只有「小池子 + 原始引擎」会出现泄露，泄露的响应全部是 HTTP 200
- 只看状态码的测试全部通过，canary 测试能找出每一条泄露
- 任意一种修复（引擎拦截或扩大 KV 池）都能让泄露归零

## 启示与可以继续尝试

- 自部署推理服务时，在启动日志里核对「KV 池容量 ≥ 声明的上下文长度」，每次改权重、量化、并行度或显存参数后都要重新核对
- 长上下文测试不要只看 HTTP 状态码，要检查输出内容；可以在测试请求里放唯一标记，看是否串到别的响应里
- 可以调大 `N_REQUESTS` 或改变长请求比例，观察泄露数量如何变化

## 内网复现

- 只用 Python 标准库，不需要安装任何依赖，`requirements.txt` 仅作说明
- 程序完全离线运行，不访问网络，也不需要 API key 或 GPU
- 如需对照真实修复，SGLang 的相关 PR 和 v0.5.22 发布说明需要外网或内网 GitHub 镜像查看
