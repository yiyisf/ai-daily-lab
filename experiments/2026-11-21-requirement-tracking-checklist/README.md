# 玩具实验：用需求台账闸门拦住编码 Agent 的「半成品交付」

## 目的

arXiv 论文 *SWE-CoWork*（2611.20218）在模拟企业协作的 101 项开发任务中发现：顶级模型虽能通过约 63% 的单片 fail-to-pass 测试，整单完整交付率却不足 8%。轨迹分析指出三类反复出现的断层：

1. **延迟追问无人跟进**：遇到需要找同事确认的问题时暂搁，之后再也没追回结论；
2. **已获取需求漏实现**：需求已经问清楚，改代码时却遗漏了部分子项；
3. **自报完成但测试失败**：论文中 31% 被 Agent 报告为「已完成」的需求实际上没过测试。

本实验**不调用模型、不访问网络**，只用 Python 标准库，在 6 组构造的多需求研发任务上演示一个极简的**需求台账门禁（Requirement Delivery Ledger）**：每条需求必须显式走完 `clarified` → `implemented` → `test_passed` 三个状态，且不允许存在未闭环的 `deferred_question`，否则禁止交付。

## 步骤

```bash
python main.py
```

无需安装第三方包。程序打印 6 组任务的校验明细、`METRIC:` 指标、`[PASS]/[FAIL]` 检查项和最终 `RESULT:` 结论；任一检查失败时以非零状态退出。

## 预期结果

- 6 组任务均被 Agent「自报已完成」，但其中 5 组分别存在未跟进追问、漏实现或未过测试等缺漏
- 启用需求台账门禁后，100% 拦下全部 5 组半成品交付，仅放行 1 组真正满足全部需求的完整交付

## 局限

- 本脚本检验的是结构化台账 JSON，不替代真实单元测试；它解决的是「把隐含在长对话里的多条需求外显并逐条对账」的流程问题
- 实际使用时，需要把 `test_passed` 字段绑定到 CI 或本地测试命令的真实退出码，而不是让 Agent 自己手填 `true`

## 启示与可以继续尝试

- 在开源命令行编码 Agent 的工作流里，可要求 Agent 接单后先在仓库根目录生成一个简短的 `requirements-ledger.json`（每条需求对应状态与验证命令），提 PR 前用 CI 脚本跑一遍门禁
- 这样既不用让 Agent 在对话里写冗长总结，又能防止它把半成品或未验证代码当成已完成交付

## 内网复现

- 仅依赖 Python 3 标准库，无任何第三方包，开发机与内网 CI 镜像均可直接运行
- 完全离线运行，不访问外网，不需要 API key 或 GPU
- 若接入真实项目：将 `TASKS` 替换为读取当前分支的 `requirements-ledger.json` 并在脚本里调用 `pytest` / `npm test` 校验结果即可
