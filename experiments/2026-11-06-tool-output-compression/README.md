# 玩具实验：压缩工具输出时保留错误项和离群值

## 目的

Headroom（headroomlabs-ai/headroom）在工具输出进入模型之前压缩 JSON、日志、文件等内容。README 介绍它压缩 JSON 数组时会保留错误项和统计离群值，并把原文缓存在本地，模型需要时可以按哈希取回（README 称为 CCR，可逆压缩）。

本实验**不安装、不调用 Headroom**，也不调用任何模型，只用纯 Python 演示这条思路为什么比「截断到放得下」更稳：

- 用固定随机种子生成两类模拟工具输出：
  - 服务日志：400 条记录，散落 5 条 ERROR/WARN 和 1 条延迟离群值
  - 测试报告：250 个用例，3 个失败用例在后半段
- 比较三种做法：
  - `none`：原样交给模型
  - `truncate`：只保留前 20 条
  - `smart`：字段列表 + 按级别/状态/服务计数 + 数值中位数和最大值 + 全部 ERROR/WARN/失败项 + z-score 超过 3 的离群项 + 前 3 条样例；原文按哈希存入本地缓存
- 统计每种做法的估算 token 数（按 4 字符约 1 token），以及关键条目（错误、失败、离群值对应的 id）是否还在输出里

## 步骤

```bash
python main.py
```

不需要安装第三方包。程序打印对比表、7 项 `[PASS]/[FAIL]` 检查、`METRIC:` 指标和最后一行 `RESULT:`；任一检查失败时以非零状态退出。

## 预期结果

- `smart` 比原样省下一半以上的 token，并保留全部关键条目
- `truncate` 同样很短，但关键条目都排在前 20 条之后，会被整体丢掉
- 缓存的原文可以按哈希原样取回

## 局限

- 数据是构造的，错误项刻意放在后面，用来说明截断的风险，不代表真实工具输出里错误的分布
- token 数是按字符粗估，不是任何模型分词器的结果
- 这里的 `smart` 只是按 README 描述写的极简版本，不代表 Headroom 的实际算法和压缩率；Headroom 对代码、长文本还有别的压缩器
- 结构化摘要依赖「哪些是关键条目」的规则写对；规则漏掉的异常同样会被压掉，所以需要可取回的原文兜底

## 启示与可以继续尝试

- 给编码 Agent 接测试、日志、搜索这类会返回长列表的工具时，与其截断，不如先按状态计数、只展开失败项，上下文有限的自部署模型尤其受益
- 可以把 `is_flagged()` 换成团队自己的规则（如 lint 报错级别、接口返回码），观察关键条目是否都保住
- 想试真实效果，可以在能联网的环境里按 Headroom README 安装后对比

## 内网复现

- 无第三方依赖，只需要 Python 3，开发机或内网 CI 镜像一般都有
- 程序完全离线运行，不访问网络，不需要 API key 或 GPU
- 如果想换成真实的 Headroom，需要通过内网 PyPI 镜像安装 `headroom-ai`（Python 3.11+），其文本压缩模型需要从 Hugging Face 下载，内网可先在外网下载后放入内部模型仓库
