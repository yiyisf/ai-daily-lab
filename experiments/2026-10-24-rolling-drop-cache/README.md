# 改写前缀还是管理缓存：Agent 上下文压缩的预填充成本

## 目的

论文 [Cache Engineering for Agents](https://huggingface.co/papers/2610.28577) 指出：长时间运行的 Agent 常用「上下文工程」（裁剪或摘要历史）来控制上下文长度，但改动前缀会迫使推理引擎**重新预填充**保留下来的内容；论文提出的「缓存工程」直接丢弃选定的 KV 缓存条目（Drop）、调整保留部分的位置编码（Repos），不改写轨迹、也不需要重新预填充。论文还指出，同样的 token 序列在不同操作顺序下会得到不同的缓存状态，所以只按前缀匹配复用缓存是不够的。

本实验用模拟数据演示这两点。注意：轨迹长度由脚本按固定随机种子生成，成本模型是简化的近似（只数预填充 token，不计摘要本身的生成成本，也不模拟位置重排），**不复现论文中的任何数字**。

## 步骤

1. 生成一条 60 轮的工具调用轨迹：每轮一段 Agent 输出（150–600 token）和一个长尾分布的工具返回
2. 比较三种策略：
   - `full`：保留全部历史，只增量预填充新内容
   - `summarize`：活跃上下文超过 40,000 token 时压缩成 3,000 token 的摘要，之后重新预填充「系统提示 + 摘要」
   - `rolling_drop`：只保留最近 4 个工具返回的 KV，更早的从缓存中丢弃，不改写前缀
3. 统计峰值活跃缓存、额外重新预填充的 token 数、摘要触发次数
4. 用一个 5 条消息的小例子演示「历史依赖」：先丢后加与先加后丢，最终消息相同，缓存内容不同

运行：

```bash
python main.py
```

程序打印 `METRIC:` 指标、`[PASS]/[FAIL]` 检查和最后一行 `RESULT:`，任一检查失败时以非零状态退出。

## 预期结果

- `rolling_drop` 的峰值活跃缓存远小于 `full`，额外重新预填充为 0
- `summarize` 也能控制峰值，但每次触发都带来重新预填充
- 历史依赖检查通过：相同的消息序列可以对应不同的缓存状态

## 启示与可以继续尝试

- 改 `KEEP_TOOL` 或 `THRESHOLD`，观察峰值缓存与重新预填充的取舍
- 丢弃工具返回会让 Agent「忘掉」原始内容；论文在基准上比较了准确率，本模拟只看成本，不能说明对准确率的影响
- 如果你的推理服务只按前缀做缓存复用，考虑在缓存键中记录操作历史，否则可能错误复用

## 内网复现

- **无需任何第三方依赖**，只用 Python 3.8+ 标准库，无需联网，可直接在内网运行
- 把 `main.py` 拷贝到内网机器执行 `python main.py` 即可
- 论文代码在 GitHub（`thu-nics/AKV`，Apache-2.0），基于 SGLang，需要 Rust 工具链、模型权重和 GPU；依赖可通过内网 PyPI 镜像安装，权重可通过内网 Hugging Face 镜像下载，本实验不依赖它
