# 玩具实验：合并没冲突，不等于两个 Agent 的改动兼容

## 目的

ParallACT 论文（arXiv 2611.00314）研究多个编码 Agent 在同一个仓库里各自处理不同需求时的问题：任务可能是「互补」的（各自有用，但必须共用一个接口），也可能是「矛盾」的（以不兼容的方式改同一段代码），简单地把两份改动合在一起，往往得不到可用的结果。

本实验**不复现论文**，也不调用任何模型，只用一个手写的小 `pricing.py` 构造四个场景，模拟两个 Agent 分别交付的改动：

| 场景 | 两份改动 |
|---|---|
| independent | A 调整包邮门槛，B 新增一个格式化函数，互不相关 |
| same-line | A 把折扣改成八折，B 改成八五折，改的是同一行 |
| hidden-semantic | A 把包邮门槛提到 200；B 让总价包含运费，验收按旧门槛写 |
| interface-mismatch | A 新建 `coupons.py` 调用 `discount_for(code)`；B 实现的函数却叫 `get_discount_rate(code)` |

每个场景先确认两个任务单独看都能通过自己的验收测试（interface-mismatch 中 A 依赖 B 的接口，单独无法验收，这是互补任务的特点），再用 `git merge-file` 做三方合并，最后在合并结果上重跑双方的验收测试。

## 步骤

```bash
python main.py
```

不需要安装第三方包。程序打印每个场景的单独验收、合并冲突块数和合并后验收结果，然后输出 5 项 `[PASS]/[FAIL]` 检查、`METRIC:` 指标和最后一行 `RESULT:`；任一检查失败时以非零状态退出。

## 预期结果

- independent：合并无冲突，合并后两边测试都通过
- same-line：git 报告冲突，只靠「有没有合并冲突」就能拦下
- hidden-semantic、interface-mismatch：合并**没有冲突**，但合并后至少一边的验收测试失败

## 局限

- 场景是手写的，规模极小，只用来说明「文本合并」和「语义兼容」是两回事，不代表论文里的任务分布或成功率
- 实验里的「Agent 改动」是固定的字符串替换，不涉及任何真实模型的行为
- 合并后重跑测试只能发现测试覆盖到的问题；验收测试本身写得不全，同样会漏

## 启示与可以继续尝试

- 让多个 Agent 并行改同一个仓库时，合并门禁至少要包括「合并后重跑每个任务的验收测试」，而不是只看有没有冲突
- 互补任务开工前，先把共用接口（函数名、参数、返回值含义）写进任务说明或规则文件，比事后合并时再对齐便宜
- 可以把自己团队真实发生过的并行改动冲突整理成类似的小场景，作为 Agent 编排方案的回归用例

## 内网复现

- 无第三方依赖，只需要 Python 3 和 git，两者通常已在开发机或内网 CI 镜像中
- 程序完全离线运行，不访问网络，不需要 API key 或 GPU
- 如果内网环境没有 git，可改用 `diff3` 等三方合并工具替换 `merge()` 函数中的命令
