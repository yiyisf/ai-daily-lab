# 玩具实验：用代码地图定位函数，比 grep 后整文件读少多少 token

## 目的

论文 How Should Agents See Code?（arXiv:2611.07286）比较了给编码 Agent 提供 AST、调用图、模块依赖等「仓库地图」的效果，发现在故障定位这类「找位置」是瓶颈的任务上，token 用量明显下降。

本实验**不调用任何模型**，只用 Python 标准库演示其中的直觉：

- 用固定随机种子生成一个模拟仓库：40 个模块、240 个函数，函数之间随机互相调用；另为每个定位目标生成 2 个只在注释和字符串里提到函数名的「诱饵」文件
- 定位任务：找出目标函数定义在哪个文件、被哪些函数调用
- 两种做法：
  - `grep`：搜函数名，把命中的文件整份读进来（模拟 Agent 常见的 grep + cat）
  - `map`：用 `ast` 建一份「定义位置 + 调用边」的代码地图，先读地图里相关的几行，再只读目标函数和调用方函数的源码
- 统计两种做法读入内容的估算 token 数（按 4 字符约 1 token）和结果是否正确

## 步骤

```bash
python main.py
```

不需要安装第三方包。程序打印每个目标的对比表、4 项 `[PASS]/[FAIL]` 检查、`METRIC:` 指标和最后一行 `RESULT:`；任一检查失败时以非零状态退出。

## 预期结果

- 两种做法都能找对定义和调用方
- `map` 读入的估算 token 明显少于 `grep`
- `grep` 会把只在注释或字符串里提到名字的诱饵文件也整份读进来

## 局限

- 仓库是构造的，函数都很短、调用关系简单；真实仓库里动态调用、同名函数、方法调用会让代码地图更难做准
- 建地图本身也有成本（程序单独打印了建一次完整地图的估算 token），只定位一两次时不一定划算
- token 数按字符粗估，不是任何模型分词器的结果
- 论文的结论是收益「因任务而异」：在测试生成任务上这些地图反而更费 token；本实验只演示定位这一类

## 启示与可以继续尝试

- 上下文有限的自部署模型做定位类任务时，可以先给它一份符号索引或调用图（脚本生成，或通过 MCP 提供），而不是让它 grep 后整文件读
- 可以把 `build_map()` 换成对团队真实仓库跑一遍，观察地图大小和定位所需读入量
- 也可以试着加入 `grep -n` 加只读命中行附近若干行的做法，作为第三种对照

## 内网复现

- 无第三方依赖，只需要 Python 3.8+（用到 `ast` 的 `end_lineno`）
- 程序完全离线运行，不访问网络，不需要 API key 或 GPU
- 如果想用真实工具生成代码地图（如 ctags、tree-sitter），需要通过内网镜像安装对应软件包
